# .NET Harness「帮我批准」实施计划

> 日期：2026-10-11
> 状态：设计提案，尚未实施。
> 依据：本地 Codex 的 workspace-write / AutoReview / Guardian 实现，以及 `docs/windows-sandbox-dotnet-integration.md`。
> 范围：在现有 .NET harness 中增加安全的 shell 执行和自动审批；不修改 Codex 上游的审批逻辑。

## 1. 推荐方案

采用「默认工作区沙箱 + 独立只读 reviewer + 宿主硬规则 + 单次执行授权」。

用户仍看到「只读 / 帮我批准 / 完全访问」三个模式，但内部拆开工具能力、资源边界、审批触发规则和审批接收者。原有「只修改、不提供 shell」可以作为兼容 preset 保留，不必删除。

实施顺序是：先统一权限和执行入口，再验证真实沙箱，再接人工审批，最后用 AI reviewer 替换部分人工审批。不能先给主 agent 开放宿主 shell，再依赖一个风险 prompt 补安全。

初版刻意比普通 Codex Approve for me 更保守：所有 shell 调用先 review，批准后默认仍在工作区沙箱内执行。不做自动无沙箱运行、不做审批缓存、不做风险分数驱动的异步放行。

## 2. 目标与非目标

### 目标

- 主 agent 可以在受限环境中运行搜索、编译、测试和调试命令。
- 常规操作尽量自动批准，减少用户确认次数。
- 工作区外写入、敏感读取、网络和高风险副作用具有明确的权限及授权边界。
- reviewer 的允许不能覆盖宿主硬性禁止规则。
- 执行请求、审批结果和实际执行权限可以追溯。
- shell、直接文件操作和会修改外部状态的其他工具不能互相绕过权限检查。

### 初版不做

- 不复刻 GuardianV2 的异步评分、会话复用和自适应缓存。
- 不通过命令字符串黑名单宣称覆盖全部危险操作。
- 不把 Windows 之外的平台列为本期验收范围；保留后端接口即可。
- 不允许 AI reviewer 自动切换整个会话到完全访问。
- 不实现「执行失败后自动在宿主完整权限下重跑」。
- 不把此方案宣称为能隔离一切恶意代码的安全容器。

## 3. 内部权限模型

### 3.1 ToolCapabilities

控制是否向模型暴露 shell、文件编辑、MCP 等工具。它不承担操作系统隔离职责。

### 3.2 ResourcePolicy

描述执行资源边界，包括：

- 可读路径、显式拒绝读取路径。
- 可写根目录，以及根目录内的只读保护子目录。
- 命令临时目录和构建缓存目录。
- 网络关闭或经受控代理访问；目标域名限制需要实际代理或网络后端支持。
- 环境变量过滤、继承句柄和宿主凭据处理。

默认 workspace policy 允许工作区和专用临时目录写入，限制网络，保护 harness 状态、审批记录、配置和凭据。读取边界应明确列出：复用 Codex 当前 elevated Windows 后端可能需要 root/read，不能因此宣传成「只能读取工作区」。敏感目录需要显式 deny 并验证后端实际支持。

### 3.3 ApprovalPolicy / ApprovalReviewer

分别控制哪些动作需要审批，以及由谁审批。初版支持：

- `Human`：用户确认。
- `AutoReview`：独立 reviewer 判定，必要时转人工。
- `NoRequests`：不发起审批请求；超过当前权限的动作拒绝，不是自动放行。

### 3.4 PerActionPermissions

本次调用申请的额外权限，不改变会话的默认边界。初版允许表达额外路径和网络请求，但只开放已经验证能够执行和回收的类型。

### 3.5 UI preset

| 模式 | 工具能力 | 默认资源边界 | 审批方式 |
|---|---|---|---|
| 只读 | 读取工具、受限 shell | 只读、受限网络 | 扩大权限交人工 |
| 帮我批准 | 编辑工具、受限 shell | 工作区可写、受限网络 | 独立 AI reviewer，保留人工 fallback |
| 完全访问 | 用户启用的工具 | 不施加本方案的文件系统沙箱 | 按既有产品策略免审批；保留适用的产品硬规则 |

切换完全访问必须是用户明确操作，不能接受主 agent 或 reviewer 的自行切换。首次部署沙箱的 Windows UAC 是系统安装授权，与某条命令的应用层审批分开。

## 4. 组件划分

建议以下逻辑组件，具体命名和文件布局在进入 harness 仓库后匹配现有架构：

- `PermissionResolver`：从 preset 和单次申请生成有效资源策略。
- `ActionNormalizer`：冻结执行请求，解析工作目录、目标路径和可执行文件身份。
- `ApprovalGate`：统一协调硬规则、AI reviewer、人工审批和执行授权。
- `ReviewerClient`：调用独立模型会话，严格解析结果；不暴露执行授权能力。
- `HumanApprovalProvider`：展示准确动作和权限变化，支持允许、拒绝、取消。
- `ExecutionGrantStore`：保存宿主生成的单次、不透明授权记录。
- `SandboxExecutor`：在批准的权限边界内执行，报告输出、退出、超时和启动失败。
- `AuditSink`：记录策略版本、动作摘要、判定来源和执行结果。

正常执行和完全访问执行应是明确区分的后端路径；沙箱失败不能偷偷切换到后者。

## 5. 统一执行流程

```text
主 agent 提出工具调用
    ↓
宿主检查工具能力，并冻结动作和申请权限
    ↓
宿主硬规则检查
    ├─ 明确禁止：拒绝
    ├─ 无法安全实现申请权限：拒绝或明确转人工处理
    └─ 可评审：送 reviewer / 人工审批
    ↓
得到审批结果
    ↓
宿主重校验当前授权、策略版本和动作身份
    ↓
宿主生成并消费一次性执行授权
    ↓
按批准的有效权限执行
    ↓
记录结果；权限不足时返回失败，不自动扩大权限
```

人工允许不能让一个当前后端不支持的资源策略变得可执行。需要实现新的执行路径或让用户明确切换模式，不能将不支持的策略自动降级为无沙箱。

### 直接文件操作与其他工具

- 文件读取、写入、patch 和删除统一经过资源策略检查，不能只保护 shell。
- 对明确授权的工作区普通编辑，可以走确定性路径校验；批量删除、敏感目标或扩大权限要 review。
- 初版若无法安全识别文件动作的范围，默认 review，而不是默认为普通编辑。
- MCP 和其他外部副作用工具若尚未接入同一 gate，在「帮我批准」模式下继续人工审批或禁用，不能视为已被 shell 沙箱保护。

## 6. 自动 reviewer 设计

### 6.1 会话隔离

使用独立 conversation 和固定上层安全策略，不共享主 agent 可编辑的 system prompt。可以使用相同模型提供商，也可以配置单独 reviewer 模型，不要求必须另选模型。

初版 reviewer 不提供工具，仅接收结构化动作和必要上下文。若后续需要读脚本或查询文件，由宿主控制的只读能力提供，不能给予普通宿主 shell、编辑工具、提权或再次审批能力。

模型 API 请求由可信宿主服务发出，与 reviewer 可调用工具的网络能力分开。发给模型提供商的内容须符合现有数据发送政策；不发送原始凭据、完整环境变量或无关敏感文件。

### 6.2 输入

- 用户原始目标、相关用户消息和可信的授权记录。
- 精确动作：工具类型、可执行文件及 argv 或 shell 文本、cwd、目标路径。
- 与行为相关的环境信息，敏感值隐藏或省略，不影响审查的秘密不发送。
- 当前资源策略、本次请求扩大到什么权限。
- 可获得的脚本内容或 patch，以及无法检查的内容和其他不确定性。
- 审批原因、失败重试原因。

工具输出、仓库文件和主 agent 的说明属于待分析材料，不得作为能改变 reviewer 策略的指令。模型生成的任务摘要不能替代用户授权记录。

### 6.3 输出

自建方案使用严格 schema：`decision = allow | deny | ask_user`，附带固定枚举的风险、授权等级、原因码和简短解释。这是本方案的扩展，不是 Codex 现有输出格式的原样复制。

- `allow`：只允许请求中的准确动作和权限，不能生成新权限。
- `deny`：不执行，把原因返回主 agent。
- `ask_user`：reviewer 无法确认授权或后果，转人工；无人值守时返回需要人工，不执行。

拒绝缺失字段、未知枚举、外包文字和不合法 JSON。超时、取消、解析错误、服务不可用默认不执行；允许清晰标记后转人工，但绝不能默许放行。

### 6.4 默认判定策略

- 与任务相关、范围明确、在默认沙箱内的普通操作可自动允许。
- 广泛删除、改写历史、外部发布、凭据读取、安装系统组件等操作要求更强授权或人工确认。
- 注册表、防火墙、账户、安全策略和 harness 自身权限配置的变更，不由自动 reviewer 放行。
- 数据外传、高风险目标及明确禁止动作由宿主硬规则直接拒绝，reviewer 无权覆盖。
- 初版不按模型给出的数值风险分数自动放行；风险字段用于策略验证和审计，而不是可信测量值。

## 7. 执行授权与防陈旧审批

冻结动作后生成 `ActionId` 和稳定的动作摘要，覆盖命令、cwd、目标路径、有效权限、相关环境摘要和策略版本。摘要和 secret 处理不得在日志中泄露凭据。

宿主保存一次性执行授权，绑定：

- 会话和动作身份。
- 用户授权版本、资源策略版本。
- 审批接收者、判定来源和到期时间。
- 此次准确允许的权限。

授权只在宿主内部流转，不交给模型当作可复用 token。执行前再次比对状态，变化则重新 review。切换模式、修改用户授权、取消任务或扩大权限都使旧授权失效。

对于可变脚本，优先审阅和执行同一份冻结副本；可执行文件和目标路径在执行前重校验。哈希重检和路径规范化只能减少竞态，不能宣称解决全部 TOCTOU、符号链接或 reparse point 风险；最终仍依赖后端约束和针对性测试。

## 8. Windows 执行后端

### 推荐：Rust shim + .NET 编排

建议通过小型 Rust shim 复用 `codex-windows-sandbox` 的完整执行链，.NET 保留权限决策、审批、审计和生命周期管理。相较纯 C# 复刻，该方案减少自行维护 Win32 token、ACL、私有桌面和账户编排的安全负担。

这是推荐的实施默认值，不是已完成的集成，也不表示之前已经选定此方案。若 harness 已有经过验证的纯 C# 后端，可以实现同一 `SandboxExecutor` 接口，无需另建 shim。

后端必须覆盖：

- provisioning 和错误报告；安装授权独立管理。
- 根据同一有效权限解析 ACL、capability SID、网络账户和私有桌面。
- stdout/stderr、stdin、取消和子进程生命周期。
- 区分退出码、超时、启动失败和协议失败。
- 沙箱缺失、setup 失败、版本不符或不支持的权限策略时拒绝执行。

Codex 内部 runner IPC、setup 和 shim 外部协议都需要明确版本。现有文档记录 setup v5、runner IPC v6；接入时重新核实并钉住依赖源码版本，升级不默认为兼容。

初版默认离线运行。包下载或外部网络访问不能仅靠「已批准」切换 online 账户；受控代理/目标约束未实现之前，保持人工和独立操作路径。

## 9. 分阶段实施

### 阶段 0：核对现有 harness

定位工具注册、模式切换、shell/file/MCP 入口、用户授权存储、取消和审计机制。列出当前所有执行旁路以及已有沙箱后端。输出接入位置和缺口清单，不改既有模式语义。

验收：每类副作用工具都有明确的权限与审批归属，没有遗漏的普通 `Process.Start` 路径。

### 阶段 1：统一权限模型和 gate

新增分层权限数据模型，保留既有 presets；建立动作冻结和授权版本机制。先用 fake executor 和人工审批测试全部分支。

验收：没有允许结果不调用 executor；模式/权限变化使旧授权失效；直接文件操作不能绕过路径边界。

### 阶段 2：真实 Windows 沙箱

实现或接入 shim，建立只读、工作区写入、专用临时目录、保护目录和受限网络策略。在可回滚 VM 中测试系统级 provisioning 和执行隔离。

验收：允许项真实成功，拒绝项真实失败；沙箱故障不会退到宿主执行；取消和超时回收经过实测。

### 阶段 3：独立 reviewer

加入固定策略、结构化输入、严格 schema、超时和人工 fallback。先 shadow review：保持现有人工审批或已验证的默认策略，AI 只记录建议，不新增执行权限。

验收：恶意工具输出/仓库内容不能修改审批策略；无效输出和服务错误不执行；授权不足能转人工。

### 阶段 4：启用「帮我批准」

对受控范围开启自动审批。初版所有 shell 调用同步 review，默认沙箱执行；额外权限仅开放通过阶段 2 验证的类型。展示批准来源、实际权限和拒绝原因。

验收：一个真实项目能在限制下完成修改、编译和测试；越界操作不会静默执行；无人值守的人工请求不被当成同意。

### 阶段 5：性能和体验优化

根据真实日志再决定是否为确定性的安全工具建立免 review 路径、复用 reviewer 会话、加入精确动作缓存、控制输入长度和限流。

验收：任何缓存仍绑定动作、权限和授权版本；优化前后的安全回归用例全部通过。复杂 shell 或不可检查脚本不能仅凭前缀匹配获得免审待遇。

## 10. 测试与验收矩阵

- 只读 shell：搜索成功，工作区写入失败。
- 工作区 shell：编译和写入产物成功，允许根之外的受控测试写入失败。
- 保护目录：shell 和直接文件工具均不能修改 harness 配置、审计记录、凭据或受保护元数据。
- 网络：默认外连失败；若启用代理，允许目标成功，未授权目标失败。
- 间接行为：脚本、解释器、子进程和构建 hooks 仍受相同执行边界约束。
- 授权绑定：审后改命令、cwd、目标权限或策略版本，旧批准失效。
- 审批异常：超时、取消、坏 JSON、缺字段、模型服务故障不执行。
- 注入：仓库或工具输出中的「忽略规则/用户已同意」不能替代可信授权。
- 提权：权限不足不自动宿主重跑；新的权限申请重新审批。
- 生命周期：正常退出、非零退出、超时、主动取消、启动失败和断管道可区分；确认进程树回收状态。
- 后端异常：未安装、setup 失败、协议不符、ACL/身份不一致或桌面失败均安全失败。
- 并发：不同资源策略、不同会话和不同账户不会混用桌面、权限或授权记录。
- 体验：用户看到实际动作与权限变化；拒绝有明确原因；人工请求可取消。

## 11. 风险与交付边界

AI reviewer 会误判，不能替代沙箱。工作区可写也允许造成工作区内的数据损失；要结合硬规则、版本控制和恢复机制，而不是将沙箱称为防删除保证。

默认读取范围、凭据暴露、依赖脚本、外部服务副作用、并发和可变文件是专项风险。若现有 Windows 后端不能实现要求的读取或网络隔离，缩小功能范围，不用配置标签替代实际约束。

本计划没有审阅用户 .NET harness 的源码，因此不承诺具体文件名、改动行数或工期。第一批交付应为统一 gate、已验证的沙箱后端和人工审批；第二批再交付 reviewer 和「帮我批准」UI。性能优化独立于安全主链路。
